### 选型决策门槛

- **Kafka**：只有在下游限速测试显示 Redis Stream 积压无法在目标恢复窗口内消化，或需要跨服务重放/多消费者隔离时引入；当前无实测依据直接切换。
- **EMQX 集群**：单节点故障实验不能证明集群能力。必须在至少 3 节点环境验证连接分布、会话恢复、重连峰值和消息丢失率后再定节点规格。
- **时序库**：必须用真实报文大小、标签基数、批量和保留策略比较 InfluxDB/TDengine；当前不能根据文章中的“10～50 倍”选型。

新增待办：建立专用压测租户/设备种子和短期令牌，避免使用生产账号；在认证通过后重新记录 HTTP、MQTT、Redis/时序写入、DLQ 与资源指标。

## 实施顺序

1. 完成 P0 容量模型校准和四类压测。
2. 补消息幂等/DLQ/背压与影子原子更新。
3. 将控制改为异步状态机，之后再引入 Kafka 和 Broker 集群。
4. 用实测结果决定时序库和节点规格，再推进多地域。
